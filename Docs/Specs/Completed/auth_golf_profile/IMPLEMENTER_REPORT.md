## Defects found and fixed during this task

Four, none of which the gates would have caught on their own — every one came from the
measure-then-look loop the playbook prescribes.

1. **`GPS_WELCOME_GET_STARTED` was missing from the CSV** — the primary button rendered the raw
   key. Caught by the first real-navigation capture. *Shape audit*: rather than adding the one
   row, every localization key referenced by any file this task touches was cross-checked against
   the CSV; exactly one was missing, and three apparent misses (`CHOTO`, `LEADERBOARD`, `PRIZES`)
   were comment text in `PersistentUIManager`, not keys.
2. **Every SemiBold run was ~11 % too large.** Build rule 4 encodes the correction for `Main
   Buttons` only (66 → 59), but the same face is used for all SemiBold text. Measured before:
   Intro Title w 1.109 / h 1.120, Welcome Title 1.103 / 1.107, Feature Name 1.106 / 1.095, Chip
   Label 1.101 / 1.059 — while the calibrated button sat at 1.014 / 0.978. *Shape audit*: all
   19 text sites in both builders were enumerated with a per-site verdict (6 FAIL, 13 PASS), then
   fixed in one pass with a single named constant `SemiBoldSize = 59f/66f`, from which the
   button's own 59 now falls out (`66 * 0.8939 = 59.0`). After: 0.94 – 1.01 on every SemiBold run.
3. **The pager dots were far too bright** — (161,170,180) against the node's (103,137,158).
   `GpsUiColor.A(White, 0.35f)` is genuinely translucent, so Unity composited it in linear light
   where Figma composited in sRGB (playbook §3). *Shape audit*: both translucency sites in the
   builder were checked — the dots (wrong helper, fixed to the pre-composited `#67899E`) and
   `input.selectionColor` (correctly translucent, since a selection highlight must let glyphs
   read and the node draws no selection state). After: (104,137,158), Δ 0.3.
4. **The hero-disc colour was invisible.** `S_GpsIconRing_Tile` is a *filled* navy circle with a
   gold rim, not an annulus, so the colour disc placed behind it was completely covered — the
   first build rendered identically navy in all four colours while the wiring read as correct.
   Fixed by moving the colour onto the ring's own fill (`S_AUTH_AvatarRing_*`, the same atom
   geometry with the swatch gradient), collapsing two Images into one. Caught only by looking at
   the whole captured frame.

## Spec deviations (each with its reason)

1. **`AuthService.IsSignedIn` does not exist.** SPEC §2 flagged this to verify. The real property
   is `AuthService.Instance.Session.IsAuthenticated`, which is what `SplashScreenController`,
   `AuthGate`, `LoginScreenController` and `GachaTicketManager` all use. Used that.
2. **The migration went to `backend/migrations/`, not `supabase/migrations/`.** Every migration
   since 2026-04 lives in `backend/migrations/` with a `YYYY_MM_DD_name.sql` name;
   `supabase/migrations/` holds only three files from the original schema. Followed the living
   convention.
3. **Key count is 28, not ~23, and `GPS_GOLFPROF_NAME_TAKEN` was NOT added.** The SPEC's list
   conflated the top-bar title with the in-panel heading on both screens — they are different
   strings ("GOLF PROFILE" vs "SET UP YOUR GOLF PROFILE"; "WELCOME" vs "WELCOME TO GOLFIN GPS") —
   so each became its own key (`_TITLE` / `_TITLE_INTRO`, `_TITLE` / `_TITLE_HEAD`). Added beyond
   the list: `GPS_WELCOME_SKIP`, `GPS_WELCOME_GET_STARTED`, `GPS_GOLFPROF_NICKNAME_HINT` (the node
   shows a filled field, but an empty one needs a placeholder) and `GPS_GOLFPROF_HANDICAP_BAD`.
   Dropped: `_NAME_TAKEN`, because SPEC §3 says to reuse CreateUsername's treatment and that
   screen's message is the existing `AUTH_USERNAME_TAKEN` — inventing a second key for the same
   sentence is what "don't invent" rules out.
4. **No input shake exists to reuse.** SPEC §3 asked for "the input shake/red used elsewhere if
   one exists, else just refuse SAVE (NOTE which)". The project has no such treatment
   (`ButtonPressFeedback` is a press scale, nothing else). So: SAVE is refused and the reason
   appears in the same red error label the name rules use. NOTED, as asked.
5. **Handicap is range-checked, not only parsed.** The column is `NUMERIC(5,1)`; a value ≥ 10000
   would come back as a 500 rather than as something the player can act on. Accepted range is
   −10…60 and the message says so.
6. **The error label is not in the node.** The node has no failure state at all. It is placed in
   the `Spacer` band directly below the panel so it can never disturb the panel's own layout, and
   starts inactive.
7. **`PUT /user/update` cannot clear a field to NULL** — and this is worth Cesar's attention, not
   just a footnote. It is the exact flip side of the "omitted means preserved" property proven in
   the round trip: null and omitted are indistinguishable on the wire. Restoring the dev account
   therefore needed a direct PostgREST write. **The future Settings screen that "you can change
   all of this later" promises will need either an explicit-null contract or a dedicated clear
   endpoint** if a player is ever allowed to un-set their handicap.
8. **Two extra ring sizes were added to `make_gps_icon_ring.py`** rather than scaling
   `S_GpsIconRing_Tile` to 150/96. Scaling lands the stroke at 8.52 / 5.45 instead of the node's
   8.33 / 5.33; the atom's own baker gives the exact token for one line each. Re-running the
   baker leaves the two existing rings byte-identical (verified: clean `git status`).

## Needs manual verification

1. **The 409 duplicate-nickname path.** The branch and its message are in place and share
   `CreateUsername`'s exact treatment, but provoking a real 409 needs a *second* account whose
   `display_name` collides — the dev account can always rename to its own name. Two accounts on
   one device is a Cesar-side setup.
2. **On-device keyboard behaviour.** `shouldHideMobileInput = true` and
   `ContentType.DecimalNumber` are set on both fields (so a real player cannot type `abc` into the
   handicap field at all — the error path exists as a second layer, reached in the capture by
   setting `.text` directly). Neither the numeric keypad nor the hide-input-bar behaviour is
   observable in the Editor.
3. **Japanese layout.** All 28 keys carry JA, but the JA strings were not previewed in the Editor
   on purpose: switching language there rebakes the NotoSansJP SDF atlas (7 KB → 2.2 MB of
   churn). Worth one look in a JA build, especially "ハンディキャップ（任意）" against the 878px
   field label.
