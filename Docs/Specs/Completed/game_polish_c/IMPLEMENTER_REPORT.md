## 0 · What this task turned out to be

The SPEC framed it as "small, mechanical". Two of the three sweeps were. The third was not, and
the reason is worth the top of the report:

**C3's first three runs reported 32/32 surfaces clear, and all three were wrong.** The probe
resolved the device's safe-area inset once at start-up and then measured every surface against
`Screen.height` — and the Editor's play-mode view changed size under it mid-route. One run
computed "band starts 676" on a 2796-tall device, which is only possible if the height had become
853. Once the probe re-resolved per surface and recorded the view each verdict was measured at,
the same route found **two real intrusions**: 20 px of `BOOST STAMINA` behind the Dynamic Island,
and the TOURNAMENTS entry button grazing it by 0.6 px.

So the C3 "before" figure in this report is not the first measurement taken — it is the first
**trustworthy** one, and the earlier runs are discarded rather than quoted. §C3 says "measure,
don't assume"; the harder half of that is noticing when your instrument is the thing doing the
assuming.

### A3 · Scroll table — **PASS**

`Docs/Diagnostics/_capture/game_polish_c_scrollrects_{before,after}.json`, [TABLES.md](TABLES.md)
§ C2, authoring table
`Docs/Diagnostics/_capture/game_polish_c_scrollfeel_authoring.tsv`.

18 in-scope ScrollRects, all now `Elastic / 0.1 / inertia on / 0.135 / sensitivity 20` — the
`gps_polish` §D9 reference. 11 were off it; 2 prefab assets and 9 scene objects were written.

**The carousels are IN scope, and the SPEC expected them not to be.** §C2 offers the five
Bag/Club/Ball/Item/Roster carousels as likely exclusions "if the controller drives position
itself". Each was checked rather than assumed: all five write `horizontalNormalizedPosition` **only**
from an arrow tap or a programmatic selection, and **none** implements `IBeginDragHandler` /
`IEndDragHandler`. A finger drag on any of them is handled entirely by the ScrollRect, so the
movement type IS what the player feels and §C2's own test puts them in scope. `ModeCarouselController`
— the one carousel that really does own its drag — has no ScrollRect at all (it lerps a layout), so
it never appears in the table.

**The SPEC's serialized reading of the enum is inverted.** `ScrollRect.MovementType` serialises as
`Unrestricted 0 / Elastic 1 / Clamped 2`. §C2's baseline reads `m_MovementType: 2` as Elastic; it is
Clamped. That is why `GachaRatesModal` is listed there as "already Elastic" when it was Clamped/40,
and why the live audit rather than the YAML is the source of truth for this table.

**Exclusions (6), each with the reason:** the two GPS lists (`GpsVoteScreen/VoteList`,
`VenuePickerModal/List`) and the four auth screens (`LoginScreen`, `SignUpScreen`,
`CreateUsernameScreen`, `ResetPasswordScreen`) — Tier 2, not this track.

**`scrollSensitivity` is unified to 20 and is not part of the feel.** It scales wheel and trackpad
deltas only, which no phone has; it is unified so two Editor sessions scroll the same list at the
same speed, and it is called out here as non-player-facing rather than sold as part of the change.

Clips: [`videos/game_polish_c_b_overscroll_rankings.mp4`](videos/game_polish_c_b_overscroll_rankings.mp4)
and [`videos/game_polish_c_c_overscroll_inventory_items.mp4`](videos/game_polish_c_c_overscroll_inventory_items.mp4).
Both drags go through the ScrollRect's own `OnBeginDrag` / `OnDrag` / `OnEndDrag` with real
`PointerEventData`, never by writing `normalizedPosition` — writing the position moves the content
without engaging the movement type at all, so the clip would look identical whether §C2 had run or
not. It would be a recording of the harness, not of the change.

### A6 · Toast fade — **PASS** (the eased version; see D-1)

`ToastFadeParityTests` (7 tests) and `Docs/Diagnostics/_capture/game_polish_c_toast_fade.txt`.

**Cesar's call, 2026-09-08: ship `UiMotion.Fade`.** The toast now eases the way every other fade in
the app eases (cubic ease-out) instead of running at a constant rate. §A6's written tolerance of
0.01 was framed as "zero visible change" and is superseded by that decision — this change is
**38× it**, deliberately.

**Measured off the running coroutine, not off the primitive.** `GamePolishProbeC`'s `toast` mode
calls the real `ToastController.Show()` — the public API every caller uses — and samples
`_canvasGroup.alpha` every frame:

```
# duration 0.3s, 21 frames, unfixed clock
# best-fit start offset       = 0.017s (~1 frame at 60 fps)
# worst |alpha - easeOut(t)| = 0.0024   <- best fit
# worst |alpha - linear(t)|  = 0.2726
# verdict: the shipped fade is EASE-OUT -> PASS
```

Still frame: `screenshots/after_01_toast_midfade__Home.png`.

**The start offset is fitted, not assumed, and the first run got that wrong.** `Show()` starts a
coroutine that runs its first step inside the same frame, so the sampler's first reading already
had alpha at 0.159 — at what it called t = 0. Scored against a fixed t0 the probe reported
`NOT ease-out -> FAIL` on a fade that is demonstrably eased; it was measuring the interleaving of
two coroutines. The offset is now searched, both curves keep their best fit, and the shift
(0.017 s ≈ one frame) is printed so a reader can see it is timing rather than something suspicious.

**What the unit tests pin,** since the arithmetic alone would keep passing if the call site were
rewired:

| test | pins |
|---|---|
| `FadeIn_RunsOnTheSharedEaseOut` / `FadeOut_…` | every frame equals `Lerp(from, to, EaseOut(t))` on both real durations |
| `FirstFrame_IsTheStartValue` | `Fade` writes `from` on frame 0 — the old loop began one step in and never did |
| `LastFrame_IsTheEndValue` | settles exactly on `to` |
| `DurationAndFrameCount_AreUnchanged` | 0.3 s / 0.5 s and the step counts are what they were; only the shape between the endpoints moved |
| `TheChangeIsTheEase_AndItIs0point385` | the divergence from the old linear loop is 0.385 at t = 0.423 — asserted, so the number this decision rests on cannot quietly stop being true |
| `ToastController_RoutesThroughUiMotionFade` | the call site itself, read off the shipped source with comments stripped |

**One behavioural improvement came free.** The old loop never wrote `from`; it began at
`Lerp(from, to, dt/dur)`. `UiMotion.Fade` sets the start value on its first frame, so a toast
re-`Show()`n mid-fade now starts from a defined alpha instead of wherever the interrupted fade had
reached.

### A7 · Lint delta zero — **PASS**

The linter's render-health layer reads sprites, colours, `Image.Type`, 9-slice scaling, sizes and
text metrics. A scan of the entire prefab + scene diff for every property in that set:

```
CHANGED/REMOVED visual properties: NONE
```

Not one property that can move a rendered pixel changed on any object that already existed. The
additions are the 256 new components' `m_Enabled: 1` and the two new `SafeArea` wrappers — each a
`{0,0}-{1,1}` stretch with zero `sizeDelta`, i.e. a container that cannot move a child.

**This scan found a real defect.** `SafeAreaFitter` is `[ExecuteAlways]`, so `AddComponent` runs its
`Awake` → `Apply()`, which writes anchors computed against whatever `Screen` the Editor reports at
that moment. Stretching the wrapper first and adding the component second baked
`anchorMax (1.7598909, 1.6389236)` into `StaminaShopSelectionScreen.prefab` — a wrapper 76 % wider
than its parent at rest. It self-corrected at runtime (Awake re-applies), so nothing looked wrong.
The builder now stretches **after** the component exists; the prefab was reverted and rebuilt, and
the serialised value is the neutral stretch.

## 4 · Deviations

- **D-1 · `ToastController` uses `UiMotion.Fade`, and the toast now eases — RESOLVED by Cesar,
  2026-09-08.** §C4 asked for both `UiMotion.Fade` and a per-frame alpha log within 0.01 of the old
  loop, and those are not compatible: `Fade` eases on cubic ease-out, the old loop was a straight
  `Mathf.Lerp`, and the curves are furthest apart at t = 0.423 where `1−(1−t)³ − t = 0.385` — 38×
  the stated tolerance. This shipped first on `UiMotion.Tween(…, Ease.Linear)` (exact parity, no
  visible change) with the trade put to Cesar; he chose the eased version. Over the 0.3 s fade-in
  the toast now reaches most of its opacity in the first third and settles gently rather than
  ramping evenly. The durations, the frame count and the endpoints are unchanged; only the shape
  between them moved, and `TheChangeIsTheEase_AndItIs0point385` asserts by how much.

- **D-2 · The five carousels are in scope; the SPEC expected exclusions.** See A3. Checked, not
  assumed: none of the five implements a drag handler.

- **D-3 · The scene diff is isolated, not committed as saved.** Saving `ShellScene.unity` after it
  has been opened or played re-serialises ~530 lines of values that a LayoutGroup, TMP auto-sizing
  or a Scrollbar computed — anchors, sizes, font sizes, scroll positions. None of it is authored,
  all of it is noise, and the first save buried a 2,100-line change under a 4,700-line diff (project
  memory: `scene_save_bakes_layout_churn`). `Docs/Scripts/filter_scene_churn.py` keeps a hunk only
  when it changes something outside that derived set; the result was reloaded into the Editor and
  every gate re-run against the committed file. The scene's final diff removes **13 lines**: nine
  `m_ScrollSensitivity`, one `m_MovementType`, the ModeSelection re-parent, and one cosmetic
  `-0`-formatted rotation. A7's scan above is the independent check that nothing else moved.

- **D-4 · The simulator pass measures and does not capture.** `CaptureCore`'s shutter yields on
  `WaitForEndOfFrame` and reads the GameView's render texture; with the Device Simulator as the
  play-mode view there is no GameView rendering, and a sim run hung there for ten minutes without an
  exception, one surface into the route. So the C3 gate is the invariant JSON
  (PIPELINE_HARDENING §3: the JSON decides, the picture is for the reader) and the stills come from
  the 1170×2532 pass. Related: the Simulator only becomes the play-mode view when **no** GameView is
  open — with one docked, Unity picks it, the simulator renders nothing, and `Screen.safeArea` is the
  whole view. `EnsureSimulator` now closes the GameView and `CloseSimulator` puts it back, and the
  probe writes a loud `*** FAIL ***` line if a `sim_` run finds a modelled safe area.

- **D-5 · `Assets/Resources/Prefabs` is swept as well as `Assets/Prefabs/UI`.** §"EditMode" names
  only the latter. `GachaBannerCard.prefab` lives under Resources, is spawned at runtime into the
  shop, and carries three player-facing buttons that a sweep of `Assets/Prefabs/UI` alone would
  never have seen.

- **D-6 · `Assets/Prefabs/Original/Gameplay/**` is excluded by name.** The in-game HUD is on
  § Out of scope (Notion 2195); `InGameMap.prefab`'s button is left alone with that reason recorded.
