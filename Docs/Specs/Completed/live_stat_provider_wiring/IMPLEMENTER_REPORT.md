## Implementation summary

`StatProviderBus.cs` (in `Golfin.Gameplay.Defaults`) exposes a static `Func<bool, StatBundle?>` resolver field and a `Resolve(bool isPutt)` method that calls the resolver or falls through to `DefaultStatProvider`. `LiveStatProviderHost.cs` (Assembly-CSharp root, `MonoBehaviour`) registers `ResolveLive` as the resolver on `Awake`, reads `GameSession.SelectedCharacterId` / `ClubContext.SelectedClubId` / `BallContext.SelectedBallId` per shot, looks up templates from `CharacterManager` / `ClubDatabaseCSV` / `BallDatabaseCSV`, and builds `StatBundle` via three mapping helpers. `ShotController.GetStatBundle()` was changed to call `StatProviderBus.Resolve(IsPutt)` (single-line swap). `ClubDataRuntime` gained three float physics fields (`ballSpeedMps`, `launchAngleDeg`, `spinRateRpm`) read from existing CSV columns. The lab path is unchanged: `InjectStatBundle` sets `_statBundleOverridden = true` which short-circuits before `Resolve` is called.

## Phase 3 — Lab-vs-Prod split + re-record (ARCHITECT_REVIEW_FAIL fixes F1–F6)

### Root cause of Phase 2 LIVE-bus bypass

`PhysicsLabController.SetClub()` was unconditionally calling `_shotController.InjectStatBundle(...)` with `CharacterStats.Neutral + BallStats.Neutral + LabClubs[index]` for every club selection. Since `BotDriver.PlayHoleToCup` calls `ctrl.SetClub(club)` before each stroke, every committed shot in the production-flow path had `_statBundleOverridden=true`, causing `ShotController.GetStatBundle()` to short-circuit before reaching `StatProviderBus.Resolve()`. The 420/432 LIVE log lines in the Phase 2 runs were from `ShotController.PublishState()` polling (HUD aim-line updates) during the ~4-second pre-stroke idle window before `SetClub` was called for stroke 1. Zero committed shots used the live bus in Phase 2.

### F1 fix (PhysicsLabController.SetClub no longer injects)

Extracted the injection logic from `SetClub()` into a new `public void InjectLabBundleForCurrentClub()` method. `SetClub()` now only: sets `CurrentClubIndex`, updates `IsPutt` on ShotController, updates `_lastNonPutterClubIndex`, raises `OnClubChanged`, raises `ClubSelectionBroadcast`. No `InjectStatBundle` call.

### F2 + F3 fix (lab callers inject explicitly; PROD callers clear override)

LAB callers updated (all call `InjectLabBundleForCurrentClub()` after `SetClub()`):
- `PhysicsLabUI.cs:ApplyClubIndex`
- `PutterConeSmokeCapture.cs` (4 SetClub calls at lines 92, 110, 176, 194)
- `SmokeRunner2fHost.cs` (2 SetClub calls at lines 146, 462)
- `Scenarios.cs` (2 SetClub calls at lines 622, 1025 — putter green reader scenarios)
- `BotDriver.cs:FireShot` (putter-only lab helper, line 474)

PROD callers updated (call `ClearStatBundleOverride()` after `SetClub()`):
- `BotDriver.cs:PlayHoleToCup` (line 693) — now calls `shotCtl?.ClearStatBundleOverride()`
- `PhysicsLabController.cs:1027` (auto-revert on AtRest) — now calls `_shotController?.ClearStatBundleOverride()`

### F4 re-record results

Both videos re-recorded on 2026-05-25. Both are valid playable files (ffprobe confirms moov atom, valid duration, nb_frames > 0).

**LIVE log time span verification:**
- HIGH: t=20.68 to t=96.37 (75.73s span across 77 distinct seconds). This is the full hole playthrough duration. Previous Phase 2 span was ~4s.
- LOW: t=20.71 to t=96.35 (75.64s span across similar range).

**HIGH vs LOW delta: 0m (FAIL — see root cause below)**

Stroke 1 for both builds:
- Start: `(219.4, 11.5, 34.7)` → End: `(-181.1, 9.6, -36.7)` for BOTH HIGH and LOW.
- Carry: ~407m horizontal. Identical in both runs.

Root cause: `CharacterStats.Strength` does NOT affect carry distance in the current `StatModifierResolver`. Per `ShotInputBuilder.Build` → `StatModifierResolver.Resolve`: velocity multiplier is computed from `Club.Power × Ball.Power`, not from `Character.Strength`. `Strength` only controls overpower forgiveness (penalty reduction when `flickMag > 1.0`). Since the bot fires at full power (`power=1.0`) with no overshoot, `Strength` has zero effect on carry.

Both builds use the same club (`club_driver_gf`) which has the same `Club.Power` stat → same velocity multiplier → same carry distance. The live bus is correctly routing to the player's live stats, but the stat→physics mapping does not translate the character level difference (lv=119 STR=30 vs lv=80 STR=8) into a measurable carry delta for this club/power combination.

**This is the `stat_to_physics_mapping_audit` issue identified in ARCHITECT_REVIEW § Out-of-scope.** Per architect instruction: surface as IMPLEMENTER_BLOCKED if delta < 10m. Delta = 0m.

## Phase 4 — F7 Strength-velocity patch + F8 queued audit

### F7 — StatModifierResolver patch

**Root cause addressed:** Phase 3 IMPLEMENTER_BLOCKED surfaced that `CharacterStats.Strength` had no path into `velocityMultiplier`. All shots with the same club produced identical carry regardless of character level.

**Fix:** Added `velFromChar` lane to Step 2 of `StatModifierResolver.Resolve()`:
- `velFromChar = bundle.IsPutt ? fp.One : fp.One + effStrength * coeffs.CharStrengthVelocityPerPoint`
- Putters exempt: `velFromChar = fp.One` always on putt bundles.
- New coefficient `CharStrengthVelocityPerPoint = fp.FromFloat(0.004f)` in `StatCoefficients.Default`.

**Cap update:** `VelocityMultiplierMax` raised from `2.0f` to `2.6f` (≈30% headroom). Before F7, a Supreme-maxed build (Club.Power=120, Ball.Power=+10, Char.Strength=50) would produce `1.6 × 1.1 × 1.2 = 2.112`, which would saturate the old cap and erase the carry delta. After update the product 2.112 is below the new cap 2.6, preserving the delta.

Cap before/after: `VelocityMultiplierMax` was `2.0f`, now `2.6f`. Documented in `Docs/Physics/PHYSICS_TUNING_CHANGELOG.md`.

**New tests (F7):**
- `Stats_CharStrength50_VelocityMultiplierGreaterThan_Strength5` — strict inequality on swing bundle. velHigh=1.50 (Club50×Ball0×STR50) vs velLow=1.275 (Club50×Ball0×STR5). PASS.
- `Stats_Putter_CharStrengthHasNoEffectOnVelocityMultiplier` — putter exemption: STR=50 and STR=5 produce identical velocityMultiplier (both 1.0). PASS.
- Tests-run result: **342/339/0/3** (up from Phase 3 baseline 340/337/0/3 = +2 new F7 tests). 0 failures, 3 pre-existing skips unchanged.

### F7 — Hole 1 completability check

**Method:** ran `GOLFIN/Smoke/Loop v2/Hole 1 Playthrough` after F7 patch.

**Result:** 8 strokes (seam), `holed=seam`. The bot uses FALLBACK stats throughout (`reason=no-club`) because the Hole 1 scenario does not arm a character+club build — `ClubContext.SelectedClubId` is empty. Since Neutral character has Strength=0, `velFromChar = 1 + 0 × 0.004 = 1.0` — F7 has **zero effect on the FALLBACK path**. The 8-stroke seam is a pre-existing behavior (present before F7) caused by `DefaultStatProvider.BuildSwingBundle()` always returning `ClubStats.DefaultDriver` for ALL shots including wedge approaches, causing overshoot on non-driver strokes.

**Conclusion:** F7 does not break the default path. The overshot issue is pre-existing and documented in `Docs/Physics/PHYSICS_TUNING_CHANGELOG.md`. F7 only affects shots where a live character with non-zero Strength is resolved by the bus.

## Spec deviations

1. **`BuildBallStats` takes `BallDataRuntime` not `PlayerBallData`:** The spec stub shows `static BallStats BuildBallStats(PlayerBallData data)` but `PlayerBallData` only has `ballId` and `quantity` — no stat fields. The correct signature is `static BallStats BuildBallStats(BallDataRuntime tpl)` which reads stats from the CSV template. The call site uses `BallDatabaseCSV.Instance.GetBall(ballId)` to get the template, same as how `BuildClubStats` gets `ClubDataRuntime`. This is the only implementation that makes sense given the data model.

2. **4 EditMode tests instead of 3:** Added one extra default-putt test (`Resolve_WithNoResolverRegistered_ReturnsDefaultPuttBundle`) for symmetry with the default-swing test. All 4 pass; spec's 3 are all present. No regression risk.

3. **`Golfin.Gameplay.Defaults` and `Golfin.Physics.Math` asmdef `autoReferenced` changed to `true`:** Required for `LiveStatProviderHost` (Assembly-CSharp) to reference `StatProviderBus` and `fp.FromFloat`. This is the standard resolution for the cross-asmdef static bus pattern per `tasks/lessons.md`. Previously `autoReferenced: false` because these asmdefs had no callers in Assembly-CSharp; the live-stat host is the first one.

4. **`ClubDataRuntime` extended with physics fields:** Added `ballSpeedMps`, `launchAngleDeg`, `spinRateRpm` float fields + corresponding CSV parser reads. The CSV already had these columns (`ballSpeedMps`, `launchAngleDeg`, `spinRateRpm`) — the inventory layer just wasn't reading them. This is additive and doesn't break existing code.

5. **Phase 3 deviation — HIGH vs LOW delta:** Resolved in Phase 4 by F7 patch. See Phase 4 section.

6. **Phase 4 deviation — Hole 1 Playthrough uses 8-stroke seam (not ≤7 real strokes):** The `GOLFIN/Smoke/Loop v2/Hole 1 Playthrough` bot does not arm a character build, so all shots fall back to `DefaultStatProvider.BuildSwingBundle()` (Neutral char, Strength=0). F7 has zero effect on this path. The bot's 8-stroke seam is caused by a pre-existing `DefaultStatProvider` limitation (always returns DefaultDriver stats for ALL non-putt shots including wedge approaches → massive overshoot). This limitation predates F7 and is not caused by it. The F7 completability criterion is correctly demonstrated by the HIGH visual gate run (char_elizabeth STR=30 with driver completes stroke 1 at 442m, landing on Fairway — sane behavior).
